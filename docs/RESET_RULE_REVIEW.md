# Reset / banked reset 判断逻辑复核

日期：2026-09-28。评估基线：v0.2.4，代码提交 e755190，工作区 HEAD bab0d12（仅 README 下载链接差异）。

## 结论与验证范围

当前规则能处理已收集的历史案例，但对表达变化、复合公告及证据合并不够可靠。建议保留免费、本地、无模型调用的架构，改造判断和状态流转，再评估发布。此次没有修改产品源码、替换运行中的应用或发布新版本。

- 已安装应用为 0.2.4；二进制与 dist 发布包一致，SHA-256 为 `f2dc09f5cc92ba50a10f70c077b66bff0b4e6c34ba6533501f7d4c8c40a26b44`。
- 原有 67 项测试通过。
- 新增独立审查用例 19 项：3 项历史行为对照通过，16 项针对薄弱边界的期望失败。该结果不代表真实流量错误率。
- 用例为合成文本，只有对照项沿用已知历史表达；不宣称这些合成帖子真实发生过。
- 测试在临时源码副本运行，没有真实联网抓取或写入用户应用数据。

## 主要发现

### P1：banked reset 的词语出现被当作发放行为，确认门槛不一致

位置：`ResetRadar/Parsing/AnnouncementClassifier.swift:25`、`:75`、`ResetRadar/Services/MonitorModel.swift:43`、`:445`。

一般 banked reset 文本默认成为 available。`No new banked reset for Codex users.`、询问是否会获得机会、如何使用机会的教程都会通过 isActionable。自动重置只要带未来精确日期也能跳过 confirmedAnnouncement。反过来，含 maybe 的手动机会不会主动通知，却仍能占据主窗口。

对应用例：03、04、05、11、12。此前“主窗口只展示已确认预告”的表述仅对 lead 成立，不适用于所有手动机会和自动重置。

建议：把可信来源、明确发放/重置动作、肯否定、陈述/疑问、时间阶段分别判定；窗口、声音、通知共用同一份决策。历史教程、疑问、否定不建立新机会。来源未核实的线索可进入详情候选区，不触发强提醒。

### P1：预告规则过度依赖历史原句

位置：`AnnouncementClassifier.swift:15`、`:16`、`:17`、`:29`、`:102`；`MonitorModel.swift:455`。

`I promised a reset for Tuesday` 能提醒，把 Tuesday 换成 Wednesday 则不能。明确的 `More resets coming next week for Codex` 也不提醒。已给出未来发放时间的 banked reset 会因为 windowStart 尚未来到被排除，因此不能满足提前通知的需求。

对应用例：01、02、19；对照用例17。

建议：识别明确承诺的句子结构，覆盖日期/星期变化；可信来源已宣布重置但时间不精确时仍通知一次，并标注“时间待确认”。对未明确自动或手动的 reset 保留“类型待确认”。手动机会须区分“已宣布/等待发放”和“已可使用”，前者可以提前通知但不可显示为已到账。

### P1：全文关键词优先级把不同事件和不同句子的含义混在一起

位置：`AnnouncementClassifier.swift:7`、`:32`、`:37`、`:54`。

`Codex resets all propagated. We will reset Codex again tomorrow.` 被整体判成已完成；新一次预告丢失。明确承诺后面写 `Quality will likely improve`，likely 会让整篇承诺降为不确定。`limits reset for ... tomorrow` 也被完成短语误吞。手动机会发放完成后写 `It is done` 会进入 announcedComplete，反而不提醒用户去使用。

对应用例：06、07、08、14；对照用例16。

建议：按句子/分句及事件对象解析。完成只能结束同一次事件；同文中的下一次重置独立保存。自动重置完成意味着旧倒计时结束；手动机会发放完成意味着机会可用，两者状态不可共用。否定、不确定词须限定作用范围。

### P1：时间没有绑定到对应动作

位置：`AnnouncementClassifier.swift:38`、`:65`；`ResetRadar/Parsing/TimeResolver.swift:13`、`:23`。

全文寻找第一个可解析日期。公告同时写“28日发放、30日过期”，会把28日误用作失效时间；先写故障开始时间再写重置时间，会把故障时间用于倒计时。

对应用例：09、10。

建议：先区分重置执行、机会发放、机会失效、故障/发帖时间，再为每个动作解析日期和时区。只有语义、日期、时区都明确时才生成精确倒计时。只有星期/晚上/下周的预告保留原文或范围，不编造到秒的时间。

### P1：后读取的弱摘要能覆盖原帖结论

位置：`ResetRadar/Services/EventReconciler.swift:51`、`:56`；`MonitorModel.swift:143`。

同一帖子先读到 `Codex limits will reset tomorrow` 时确认预告成立，随后读到 `Codex reset expected tomorrow` 的摘要，会把 confirmedAnnouncement 改为 false。监控按固定来源顺序读取，后续摘要能够取消前面的已确认提示。

对应用例：13。

建议：显式记录原文/转述/人工输入的来源身份和证据等级；字段更新依据证据强度与原帖修订，不依据读取先后。镜像同一帖子不能算独立交叉验证。更弱摘要不能抹除更强证据的结论；真正撤回需明确的同事件取消或更正。

### P2：产品范围、跨帖关联和24小时归档仍有缺口

位置：`AnnouncementClassifier.swift:113`、`MonitorModel.swift:59`、`:462`、`EventReconciler.swift:21`。

- 同时提到 Codex 与 ChatGPT Work 时仅保留后者；裸完成公告会推断成 astra，未必能关联原先的 codex 预告。产品双重范围丢失已由用例15复现。
- 跨帖完成关联依赖24小时内、产品相交且恰好一个候选；没有事件主体、回复关系或范围一致性的可靠约束。此项为静态代码发现。
- 没有精确倒计时的事件24小时后归档，若预告指向下周会提前消失；归档记录之后不再接受普通更新。这与此前24小时清屏需求一致，但清屏不应等于永久结束仍未实施的预告。此项为静态代码发现。

建议：产品用集合表示；未知产品保持未知，不默认猜为 astra。为同一次重置关联预告、发放、完成、补偿、更正；只有关系明确才合并。把“24小时后退出主窗口”和“事件已结束”分开，用户已用/已忽略的选择也与客观事件状态分开。

## 推荐的目标行为

| 内容 | 提醒与界面 |
|---|---|
| 可信发布者明确承诺重置，时间未确定 | 首次提醒；显示预告、时间待确认，不生成秒级倒计时 |
| 自动重置有明确时间和时区 | 提醒并倒计时；到点显示待确认，完成公告结束同次事件 |
| 将在未来发放手动机会 | 提前提醒；显示待发放，发放时间不当成失效时间 |
| 手动机会已发放/发放完成 | 提示可用；只有明确失效时间才显示失效倒计时 |
| 为受影响用户补发机会 | 提醒并清楚标注适用条件，不推定用户符合资格 |
| 旧重置完成，同时预告新一次 | 旧事件完成，新事件独立保留 |
| 问句、教程、猜测、否定 | 不当作已确认新机会，不响铃 |
| 弱来源线索 | 详情候选区显示出处与未核实状态；不触发强提醒 |

通知应以“事件+重要阶段”为依据去重。首次明确预告提醒；时间变化、范围变化、正式可用等有行动价值的更新才再提醒；相同信息换镜像或换措辞不重复响铃。

## 实施顺序与边界

1. 优先修正肯否定/问句、手动机会阶段、统一提醒门槛、证据覆盖、时间与动作绑定，并使本次复现用例通过。
2. 补充一般化预告句式、同文多事件、可靠跨帖关联及清屏与事件保留的区别。
3. 升级时重评旧证据需保留用户已用/忽略状态，并避免把规则重算批量当作新消息提醒。
4. 每次分类保留命中原句、来源等级、动作、阶段、适用范围、时间依据、是否提醒及理由，便于以后定位误报。

保持本地确定性处理，不需要每10分钟调用模型或消耗订阅额度。此方案仍不能保证理解任意自然语言；不明确时保留未知，避免猜测。来源未抓到的帖子（尤其回复）无法靠分类改进补回。本轮未审查实时来源覆盖率，不保证免费镜像覆盖所有原帖。
