# Reset Radar 0.3 判断规则

目标：尽早提醒明确的重置承诺，并尽量降低误报；本地判断，不调用模型，不消耗订阅额度。

## 提醒条件

先按句子/分句识别动作，排除无关重置、否定、问句、教程和猜测。适用资格条件（如故障期间重置失败的用户）不视为不确定猜测。可信发布者可以省略产品名；未知产品和未说明的重置类型不强行推定。

- 自动重置：明确承诺但时间不清楚时显示预告；日期、时间、时区明确才生成倒计时。到点显示待确认，完成公告结束对应的旧事件。
- 手动机会：预告、发放中、可用、失效分开。未来发放也提前提醒，发放完成不等于机会失效。失效倒计时只取失效时间，资格仍需用户在账号内核对。
- 同一篇公告可同时结束旧事件和宣布新事件。否定和完成的影响限定在对应动作，不能压掉另一个独立预告。
- 窗口、发现通知、定时提醒共用确认门槛。未核实的候选不会显示为可用机会或播放声音。

## 来源和更新

规则区分官方来源、经公共 JSON 转引的原帖、带原帖出处的社区转引和无出处社区摘要。配置内的社区摘要须有明确行动，不能只靠标题含 reset。其他作者的帖子不因来自同一个订阅源就自动成为可信承诺。这里的“原帖”仍可能由第三方转引，不意味着绕过 X 或独立完成作者身份验证。

高等级证据优先；弱摘要不能覆盖原文。相同帖子去重。有相同发布者、兼容产品范围、唯一候选和阶段推进依据的近期后续帖可合并；显式 another/again/more resets 保持独立。已关联帖子的身份持久保存，旧预告回放不倒退已发放状态。无法可靠关联的公告保持独立，避免误吞新机会。

首次明确预告、重要时间/范围变更、发放阶段更新可提醒。同样的信息重新抓取不提醒。用户标记已使用或不再显示后，重复抓取不恢复。

## 时间与保留

依据动作所在分句提取时间；发放时间与失效时间分别记录。日期解析仍限于支持的明确格式。只有“星期几”“下周”“晚上”等信息时展示待确认，不猜精确时间或时区。

支持 `tomorrow 10am PST` 和 `tomorrow at 10am PST`（含分钟与大小写变体）。“明天”从原帖发布时间在所写时区的日期计算，与查询时间及显示时区无关。原文明确写 PST / PDT 时分别采用固定 UTC−8 / UTC−7；写 PT 时使用洛杉矶当地夏令时规则，再转换成用户选择的显示时区。缺少发布时间、时区，或 PT 当地时间因夏令时切换而不存在/重复时，保留待确认。

无倒计时预告发现24小时后退出主窗口；较远预告的记录可继续保留等待后续更新（普通预告2天，星期预告8天，下周预告14天）。保留期限是监控策略，不是重置日期。精确自动倒计时归零后保留24小时待确认；明确失效的手动机会立即退出。

## 升级与验证

旧版尚未处理的证据在启动时静默重评。保留已使用、已忽略、已归档记录；升级本身不批量制造发现提醒。新增可选元数据兼容旧版存储。

测试包括规则审查中的失败样例、全星期和短回复预告、补偿资格、独立动作、发放/失效时间、取消公告、原文与摘要覆盖、多帖阶段推进、重复抓取和升级静默迁移。`ResetRadarTests/ResetRuleAuditTests.swift` 和 `RuleNotificationTests.swift` 为持续回归用例；`qa/ResetRuleAuditTests.swift` 保留0.2.4历史审查输入。

免费来源可能遗漏或延迟帖子，尤其回复；规则改进不能恢复未被来源采集的数据。确定性规则也不能保证理解任意自然语言，模糊信息保留待确认。
